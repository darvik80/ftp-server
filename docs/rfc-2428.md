# RFC 2428 — Расширения FTP для IPv6 и NAT

**Оригинал (англ.):** FTP Extensions for IPv6 and NATs<br>
**Статус:** Proposed Standard<br>
**Год:** 1998<br>
**Авторы:** M. Allman, S. Ostermann, C. Metz<br>
**Приоритет реализации:** 4 — Критично<br>
**Официальный текст:** <https://www.rfc-editor.org/rfc/rfc2428.html>

## Аннотация

Заменяет IPv4-завязанные PORT/PASV на EPRT/EPSV. Нужен для IPv6 и сильно упрощает жизнь за NAT. Без EPSV современные стеки и dual-stack окружения ломаются.

## 1 Введение

Ключевые слова вида MUST и SHOULD, встречающиеся в настоящем документе, используются в значениях, определённых в RFC 2119 [Bra97].

Протокол передачи файлов [PR85] предоставляет возможность передавать сведения только о соединениях данных поверх IPv4. FTP исходит из того, что сетевые адреса имеют длину 32 бита. Однако с внедрением шестой версии протокола Internet Protocol [DH96] адреса перестанут быть 32-битными. В RFC 1639 [Pis94] описаны расширения FTP, позволяющие использовать его поверх различных сетевых протоколов. К сожалению, этот механизм может давать сбой в многопротокольной среде. В переходный период между IPv4 и IPv6 FTP необходима возможность согласовывать сетевой протокол, который будет использоваться для передачи данных.

Настоящий документ специфицирует способ, которым FTP может передавать сведения о конечных точках соединения данных для сетевых протоколов, отличных от IPv4. В этой спецификации команды FTP `PORT` и `PASV` заменяются на `EPRT` и `EPSV` соответственно. Документ построен следующим образом. Раздел 2 описывает команду `EPRT`, раздел 3 — команду `EPSV`. Раздел 4 определяет порядок использования этих двух новых команд FTP. Раздел 5 кратко излагает соображения безопасности. Наконец, раздел 6 содержит выводы.

<a id="section-2"></a>

## 2 Команда EPRT

Команда `EPRT` позволяет задать расширенный адрес для соединения данных. Расширенный адрес MUST состоять из сетевого протокола, а также сетевого и транспортного адресов. Формат `EPRT`:

```
EPRT<space><d><net-prt><d><net-addr><d><tcp-port><d>
```

За ключевым словом команды `EPRT` MUST следовать ровно один пробел (ASCII 32). После пробела MUST быть задан символ-разделитель (`<d>`). Символ-разделитель MUST быть одним из символов ASCII в диапазоне от 33 до 126 включительно. Рекомендуется использовать символ `|` (ASCII 124), если только он не совпадает с символом, необходимым для кодирования сетевого адреса.

Аргумент `<net-prt>` MUST быть номером адресного семейства, определённым IANA в последней редакции RFC «Assigned Numbers» (на момент написания настоящего документа — RFC 1700 [RP94]). Этот номер указывает протокол, который следует использовать (и неявно — длину адреса). В настоящем документе два номера адресных семейств из [RP94] приводятся в качестве примеров, согласно следующей таблице:

| Номер AF | Протокол |
| --- | --- |
| 1 | IP версии 4 [Pos81a] |
| 2 | IP версии 6 [DH96] |

`<net-addr>` — зависящее от протокола строковое представление сетевого адреса. Для двух указанных выше адресных семейств (AF Number 1 и 2) адреса MUST быть в следующем формате:

| Номер AF | Формат адреса | Пример |
| --- | --- | --- |
| 1 | точечно-десятичная запись | `132.235.1.2` |
| 2 | строковые представления IPv6 по [HD96] | `1080::8:800:200C:417A` |

Аргумент `<tcp-port>` должен быть строковым представлением номера порта TCP, на котором узел ожидает соединение данных.

Ниже приведены примеры команд `EPRT`:

```
EPRT |1|132.235.1.2|6275|

EPRT |2|1080::8:800:200C:417A|5282|
```

Первая команда указывает, что сервер должен использовать IPv4 для открытия соединения данных с узлом `132.235.1.2` на порту TCP 6275. Вторая команда указывает, что сервер должен использовать сетевой протокол IPv6 и сетевой адрес `1080::8:800:200C:417A` для открытия соединения данных TCP на порту 5282.

При получении корректной команды `EPRT` сервер MUST вернуть код 200 (Command OK). Стандартные коды отрицательного ответа `500` и `501` [PR85] достаточны для обработки большинства ошибок (например, синтаксических), связанных с командой `EPRT`. Однако требуется дополнительный код ошибки. Код ответа `522` означает, что сервер не поддерживает запрошенный сетевой протокол. Интерпретация этого нового кода ошибки:

```
5yz Negative Completion
x2z Connections
xy2 Extended Port Failure - unknown network protocol
```

Текстовая часть ответа MUST указывать, какие сетевые протоколы сервер поддерживает. Если сетевой протокол не поддерживается, формат строки ответа MUST быть таким:

```
<text stating that the network protocol is unsupported> \
    (prot1,prot2,...,protn)
```

И числовой код, указанный выше, и информация о протоколах, заключённая между символами `(` и `)`, предназначены для программ-автоматов, получающих ответ; текстовое сообщение между числовым кодом и символом `(` предназначено для человека и может быть произвольным, но оно MUST NOT содержать символы `(` и `)`. В приведённом выше случае текст SHOULD указывать, что сетевой протокол, указанный в команде `EPRT`, не поддерживается сервером. Список протоколов в круглых скобках MUST быть перечислением номеров адресных семейств через запятую. Ниже приведены два примера строк ответа:

```
Network protocol not supported, use (1)

Network protocol not supported, use (1,2)
```

## 3 Команда EPSV

Команда `EPSV` требует, чтобы сервер открыл порт для данных и ожидал подключения. Команда `EPSV` имеет необязательный аргумент. Ответ на эту команду содержит только номер порта TCP, на котором сервер ожидает подключения. Формат ответа при этом похож на аргумент команды `EPRT`. Это позволяет использовать одни и те же процедуры разбора для обеих команд. Кроме того, такой формат оставляет место для сетевого протокола и (или) сетевого адреса, которые могут понадобиться в ответе на `EPSV` в будущем. Код ответа для входа в пассивный режим с использованием расширенного адреса MUST быть `229`. Интерпретация этого кода согласно [PR85]:

```
2yz Positive Completion
x2z Connections
xy9 Extended Passive Mode Entered
```

Текст, возвращаемый в ответ на команду `EPSV`, MUST иметь вид:

```
<text indicating server is entering extended passive mode> \
    (<d><d><d><tcp-port><d>)
```

Часть строки, заключённая в круглые скобки, MUST быть в точности той строкой, которая нужна команде `EPRT` для открытия соединения данных, как описано выше.

Первые два поля, находящиеся в скобках, MUST быть пустыми. Третье поле MUST быть строковым представлением номера порта TCP, на котором сервер ожидает соединение данных. Сетевой протокол, используемый соединением данных, будет тем же сетевым протоколом, который используется управляющим соединением. Кроме того, сетевой адрес, используемый для установления соединения данных, будет тем же сетевым адресом, который используется для управляющего соединения. Пример строки ответа:

```
Entering Extended Passive Mode (|||6446|)
```

Стандартные коды отрицательного ответа `500` и `501` достаточны для обработки всех ошибок, связанных с командой `EPSV` (например, синтаксических).

Когда команда `EPSV` выдаётся без аргумента, сервер выбирает сетевой протокол для соединения данных исходя из протокола, использованного для управляющего соединения. Однако в случае проксирующего FTP этот протокол может оказаться неподходящим для связи между двумя серверами. Поэтому клиент должен иметь возможность запросить конкретный протокол. Если сервер вернёт протокол, не поддерживаемый узлом, который будет подключаться к порту, клиент MUST выдать команду `ABOR` (abort), чтобы позволить серверу закрыть ожидающее подключение. После этого клиент может послать команду `EPSV` с запросом конкретного сетевого протокола, следующим образом:

```
EPSV<space><net-prt>
```

Если запрошенный протокол поддерживается сервером, он SHOULD использовать этот протокол. Если не поддерживается, сервер MUST вернуть сообщение об ошибке `522`, описанное в разделе 2.

Наконец, команда `EPSV` может использоваться с аргументом `ALL`, чтобы сообщить трансляторам сетевых адресов, что команда `EPRT` (как и другие команды, связанные с данными) больше использоваться не будет. Пример такой команды:

```
EPSV<space>ALL
```

При получении команды `EPSV ALL` сервер MUST отклонять все команды настройки соединения данных, кроме `EPSV` (то есть `EPRT`, `PORT`, `PASV` и т. п.). Использование команды `EPSV` таким способом подробнее объясняется в разделе 4.

<a id="section-4"></a>

## 4 Использование команд

Для всех передач FTP, когда управляющее соединение и соединения данных устанавливаются между одними и теми же двумя машинами, MUST использоваться команда `EPSV`. Применение команды `EPSV` повышает производительность передач, проходящих через межсетевые экраны или трансляторы сетевых адресов (NAT). В RFC 1579 [Bel94] рекомендуется использовать пассивную команду, находясь за межсетевым экраном, поскольку экраны обычно не разрешают входящие подключения (которые необходимы при использовании команды `PORT` (`EPRT`)). Кроме того, использование `EPSV` в определении настоящего документа не требует, чтобы NAT изменял сетевой адрес в транслируемом трафике. NAT пришлось бы менять адрес, если бы использовалась команда `EPRT`. Наконец, если клиент выдаёт команду `EPSV ALL`, трансляторы, возможно, смогут поставить соединение на «быстрый путь» через транслятор, поскольку команда `EPRT` никогда не будет применяться и, следовательно, преобразование полезной части сегментов никогда не потребуется. Когда клиент ожидает только двусторонние передачи FTP, он SHOULD выдать эту команду как можно раньше. Если клиент позже обнаружит, что после выдачи `EPSV ALL` ему необходимо выполнить трёхстороннюю передачу FTP, MUST быть начата новая сессия FTP.

## 5 Вопросы безопасности

Авторы не считают, что описанные изменения FTP вносят новые проблемы безопасности. В сопутствующем документе категории Work in Progress [AO98] более общо обсуждаются вопросы безопасности FTP и приёмы снижения соответствующих рисков.

<a id="section-6"></a>

## 6 Заключение

Расширения, специфицированные в настоящем документе, позволят FTP работать поверх различных сетевых протоколов.
