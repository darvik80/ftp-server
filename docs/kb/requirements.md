# Сводные требования по шагам дорожной карты

Единый чек-лист соответствия для всех четырёх реализаций (`ftp-server-go`,
`ftp-server-java`, `ftp-server-cpp`, `ftp-server-rust`). Источник обязательности —
только перечисленные RFC; формулировки перенесены из секций `## Что реализовать` и
`## Ключевые положения` файлов `docs/rfc-*.md`. Новых требований отсюда не брать.

Обозначения: **MUST** — обязательное нормативного RFC, **SHOULD** — рекомендованное,
**MAY** — опциональное. `[Pn]` — номер приоритета в `../index.md`. Чек-листы `## Что
реализовать` есть только в 17 страницах (список — в [README](README.md)); пункты для
остальных требований сформулированы по `Ключевые положения`.

---

## Шаг 1 — ядро протокола

Источники: [RFC 959](../rfc-959.md) `[P1]`, [RFC 1123](../rfc-1123.md) `[P2]`, [RFC 854](../rfc-854.md) `[P20]`.

### Соединения и модель сессии

| Требование | Обяз. | Источник |
|---|---|---|
| Два TCP-соединения: управляющее (порт 21, на всю сессию) и данных (открывается на передачу и закрывается после) | MUST | RFC 959 |
| Управляющее соединение — NVT ASCII, команды и ответы с CRLF | MUST | RFC 959, RFC 854 |
| Устойчивость к Telnet IAC-последовательностям в управляющем потоке | MUST | RFC 854 |
| Активный режим `PORT` и пассивный режим `PASV` | MUST | RFC 959 |
| Обязательная поддержка `PASV` (хост-требование, поверх 959) | MUST | RFC 1123 |
| Работа на multihomed-хостах (корректный выбор адреса в `PORT`) | MUST | RFC 1123 |
| Тайм-ауты и устойчивость сессии | MUST | RFC 1123 |

### Минимальный набор команд

RFC 959, «минимальный набор для рабочего сервера»: `USER`, `PASS`, `QUIT`, `PORT` или
`PASV`, `TYPE`, `MODE`, `STRU`, `RETR`, `STOR`, `NOOP`, плюс навигация `CWD`, `PWD`,
`LIST`/`NLST` и коды ответов по правилам RFC 959.

| Команда | Обяз. | Комментарий | Источник |
|---|---|---|---|
| `USER`, `PASS`, `QUIT` | MUST | аутентификация и завершение сессии | RFC 959 |
| `TYPE` (`A`, `I`) | MUST | `TYPE A` и `TYPE I` обязательны по RFC 1123 | RFC 959, 1123 |
| `MODE` (`S`) | MUST | `STREAM` — единственный обязательный режим | RFC 959, 1123 |
| `STRU` (`F`) | MUST | `FILE` — обязательная структура | RFC 959 |
| `PORT`, `PASV` | MUST | выбор хотя бы одного режима — минимум; оба — полная поддержка | RFC 959 |
| `RETR`, `STOR`, `APPE`, `DELE`, `RNFR`, `RNTO` | MUST | передача и файловые операции | RFC 959 |
| `CWD`, `CDUP`, `PWD`, `MKD`, `RMD`, `LIST`, `NLST` | MUST | каталоги (источники этих команд — [RFC 775](../rfc-775.md), нормативная редакция — 959) | RFC 959 |
| `NOOP`, `SYST`, `HELP`, `SMNT`, `STOU` | MAY | `SMNT` на практике не реализуется | RFC 959, [RFC 949](../rfc-949.md) |
| `MLST`, `MLSD`, `SIZE`, `MDTM`, `REST STREAM` | см. шаг 3 | отнесены в RFC 3659 | RFC 3659 |

### Коды ответов

| Требование | Обяз. | Источник |
|---|---|---|
| Полная система 1xx–5xx, трёхзначные коды, первый знак = класс | MUST | RFC 959 |
| Разделение позитивного/негативного/посреднического ответа по правилам 959 | MUST | RFC 959 |
| Уточнённые требования к кодам и командам хост-уровня | MUST | RFC 1123 |
| Исторические редакции кодов ([RFC 640](../rfc-640.md) `[P18]`, [RFC 630](../rfc-630.md) `[P40]`) | — | актуальная норма — RFC 959, не реализовывать |

### Чек-лист шага 1 (дословно из источников)

- RFC 959: `- [ ] Управляющее соединение NVT ASCII` · `- [ ] Активный (PORT) и пассивный (PASV) режим` · `- [ ] Команды USER/PASS/QUIT/TYPE/MODE/STRU` · `- [ ] RETR/STOR/APPE/DELE/RNFR/RNTO` · `- [ ] CWD/CDUP/PWD/MKD/RMD/LIST/NLST` · `- [ ] Система кодов ответов 1xx–5xx` · `- [ ] Типы ASCII и IMAGE`
- RFC 1123: `- [ ] Обязательные TYPE A/I и MODE S` · `- [ ] Обязательная поддержка PASV` · `- [ ] Тайм-ауты и устойчивость сессии` · `- [ ] Поведение на multihomed-хостах` · `- [ ] Уточнённые требования к командам RFC 959`
- RFC 854: `- [ ] NVT ASCII / CRLF` · `- [ ] Устойчивость к Telnet IAC`

## Шаг 2 — согласование возможностей и сеть

Источники: [RFC 2389](../rfc-2389.md) `[P3]`, [RFC 2428](../rfc-2428.md) `[P4]`, [RFC 1579](../rfc-1579.md) `[P6]`.

| Требование | Обяз. | Источник |
|---|---|---|
| Команда `FEAT` | MUST | RFC 2389 |
| Команда `OPTS` | MUST | RFC 2389 |
| Многострочный ответ формата `211-…211 End` | MUST | RFC 2389 |
| Команда `EPRT` (внешний адрес/порт/сеть, IPv4 и IPv6) | MUST для dual-stack | RFC 2428 |
| Команда `EPSV` (пассивный режим без аллокания адреса) | MUST для dual-stack | RFC 2428 |
| Код `229 Entering Extended Passive Mode (|||port|)` | MUST | RFC 2428 |
| Код `522 Network protocol not supported` | MUST | RFC 2428 |
| Запись `EPRT`/`EPSV` в вывод `FEAT` | MUST | RFC 2428 |
| Приоритет пассивного режима как режим по умолчанию для клиентов за firewall | SHOULD | RFC 1579 |
| Настраиваемый диапазон портов для данных (сценарий firewall/NAT) | SHOULD | RFC 1579 |

`RFC 959` не предусматривал стандартного способа узнать поддержки расширений — отсюда
`FEAT`; `RFC 2428` заменяет IPv4-завязанные `PORT`/`PASV` на `EPRT`/`EPSV` (формулировка
из аннотации источника). Ранний аналог — `LPRT`/`LPSV` из [RFC 1639](../rfc-1639.md)
`[P15]` — не реализовывать: смотреть RFC 2428.

## Шаг 3 — современные расширения

Источник: [RFC 3659](../rfc-3659.md) `[P5]`, [RFC 2640](../rfc-2640.md) `[P10]`.

| Требование | Обяз. | Источник |
|---|---|---|
| `SIZE` — размер файла | MUST | RFC 3659 |
| `MDTM` — время модификации (UTC) | MUST | RFC 3659 |
| `REST STREAM` — возобновление передачи в потоковом режиме | MUST | RFC 3659 |
| `MLST` — машина-читаемый факт об одном объекте | MUST | RFC 3659 |
| `MLSD` — машина-читаемый листинг каталога | MUST | RFC 3659 |
| `TVFS` — объявление однообразной файловой структуры (семантика путей) | MUST | RFC 3659 |
| Записи `SIZE MDTM MLST MLSD TVFS REST STREAM` в `FEAT` | MUST | RFC 3659 |
| UTF-8 в именах и путях | MUST | RFC 2640 |
| Токен `UTF8` в `FEAT` и `OPTS UTF8 ON` | MUST | RFC 2640 |
| Команда `LANG` | SHOULD | RFC 2640 |

Причина появления `MLST`/`MLSD`: формат `LIST` не стандартизирован жёстко (см. RFC 1123,
`Ключевые положения`).

## Шаг 4 — безопасность

Источники: [RFC 2577](../rfc-2577.md) `[P7]`, [RFC 2228](../rfc-2228.md) `[P8]`, [RFC 4217](../rfc-4217.md) `[P9]`.

### Ограничения протокола (RFC 2577)

| Требование | Обяз. | Источник |
|---|---|---|
| Защита от bounce-атак: `PORT` только на адрес клиента или полный отказ от `PORT` | MUST | RFC 2577, [RFC 438](../rfc-438.md) |
| Санитизация путей: жёсткая нормализация, запрет выхода за корень (`../`), chroot/jail | MUST | RFC 2577 |
| Политика anonymous: запрет записи по умолчанию, отдельный путь | MUST | RFC 2577, [RFC 1635](../rfc-1635.md) |
| Минимизация утечек в баннерах и ответах (версии, пути, пользователи) | SHOULD | RFC 2577 |

### Рамка безопасности (RFC 2228) — обязательна как основа FTPS

| Требование | Обяз. | Источник |
|---|---|---|
| `AUTH` (соглашение о механизме) | MUST | RFC 2228 |
| `PBSZ` (размер буфера защиты) | MUST | RFC 2228 |
| `PROT` (`C`/`S`/`E`) | MUST | RFC 2228 |
| `ADAT` (данные аутентификации) | MUST | RFC 2228 |
| `CCC` (перключение шифрования) | MAY | RFC 2228 |
| Коды безопасности `234`, `334`, `235`, `335`, `431`, `533`–`537` | MUST | RFC 2228 |

RFC 2228 не реализовывать «в вакууме» — он нужен как фундамент для FTPS (формулировка
источника).

### TLS-профиль (RFC 4217)

| Требование | Обяз. | Источник |
|---|---|---|
| `AUTH TLS` | MUST | RFC 4217 |
| `PBSZ 0` (потоковое шифрование без буфера) | MUST | RFC 4217 |
| `PROT P` / `PROT C` для данных | MUST | RFC 4217 |
| TLS на соединении данных | MUST | RFC 4217 |
| Политика обязательного TLS и `CCC` только осознанно | SHOULD | RFC 4217 |
| Implicit FTPS (порт 990) | MAY | RFC 4217 |

Минимум для рабочего FTPS, по формулировке источника: `AUTH TLS`, `PBSZ 0`, `PROT P`.

## Шаг 5 — опционально

| Требование | Обяз. | Источник |
|---|---|---|
| Команда `HOST` для виртуальных хостов, коды `220`/`504`/`530`/`550`, запись в `FEAT` | MAY | [RFC 7151](../rfc-7151.md) `[P11]` |
| Сверка имён команд и FEAT-токенов с IANA-реестром | MUST при добавлении своих токенов | [RFC 5797](../rfc-5797.md) `[P12]` |
| Политика anonymous-логина и пользовательская документация | SHOULD | [RFC 1635](../rfc-1635.md) `[P13]` |
| Понимание FTP ALG и приоритет `EPSV` в dual-stack | MAY | [RFC 6384](../rfc-6384.md) `[P14]` |
| Раздача `.cer`/`.crl` по соглашению PKIX | MAY | [RFC 2585](../rfc-2585.md) `[P22]` |

## Не реализовывать

| Тема | RFC | Почему |
|---|---|---|
| Ранние редакции спецификации FTP | 114, 133, 141, 163, 171, 172, 238, 250, 264, 265, 269, 281, 294, 309–327, 354, 385, 412, 414, 430, 438, 448, 454, 458, 463, 468, 475, 478–487, 501–542, 571, 593, 607, 614, 624, 630, 683, 686, 691, 697, 765 | бойлерплейт источников: «нормативной силы не имеет — см. RFC 959 и последующие стандарты» |
| `LPRT`/`LPSV` (FOOBAR) | 1545, 1639 | заменены `EPRT`/`EPSV` из RFC 2428 |
| `MODE B`/`MODE C` (block, compressed) | 959 (ранние идеи — 468 `[P58]`, 294) | `STREAM` достаточно, на практике редко |
| `SMNT` (монтирование структуры) | 959, 775 | не реализуется клиентами |
| FTP-mail: `XRSQ`/`XRCP`/`XSEN`/`MLFL` | 737, 743, 751, 475, 458 | исторический механизм |
| TFTP и опции TFTP | 1350, 2347, 2348, 2349, 3617 | отдельный протокол поверх UDP, не совместим с FTP |
| SFTP-1984, BFTP, ETFTP, SIFT/UFT | 913, 1068, 1986, 1440 | другие протоколы |
| OFTP (ODETTE), FTAM-шлюз | 2204, 5024, 1415 | отдельные промышленные протоколы |
| Metalink | 5854, 6249 | XML/HTTP-слой поверх загрузки, не FTP-команды |
| `ftp://` URI, административные обновления ссылок | 1738, 9141 | справочные, требований к серверу не задают |
