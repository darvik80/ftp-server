# База знаний по RFC FTP

Аналитический слой поверх страниц `docs/rfc-*.md`: темы, связи между RFC и сводные
требования по шагам дорожной карты. Страницы RFC остаются пересказами конкретных
документов, здесь же информация отфильтрована по задачам реализации.

## Страницы

| Файл | Что даёт | Когда нужен |
|---|---|---|
| [requirements.md](requirements.md) | Сводные MUST/SHOULD/MAY-требования по 5 шагам дорожной карты: соединения, команды, коды ответов, FEAT-токены, «не реализовывать» | Перед тем как писать код шага; как чек-лист соответствия для всех четырёх заглушек |
| [rfc-index.md](rfc-index.md) | Таблица всех 92 RFC: год, статус, приоритет, метка, теги, файл | Навигация и быстрый просмотр «что это за RFC» |
| [topics.md](topics.md) | Обратный индекс тема → RFC (пассивный режим, коды ответов, AUTH/TLS, UTF-8…) | Когда задача сформулирована по теме, а не по номеру RFC |
| [relations.md](relations.md) | Цепочки устаревания, явные `Отменяет/Отменён`, граф связанных RFC, расхождения в источниках | Прежде чем брать RFC из группы «Справочно / история» |

## Как читать протокол под задачу

1. Найти тему в [topics.md](topics.md) или шаг в [requirements.md](requirements.md).
2. Открыть нормативную страницу `docs/rfc-<n>.md` — только актуальная редакция даёт обязательность.
3. Проверить в [relations.md](relations.md), не заменён ли этот RFC: устаревшие редакции
   (1545, 765, 1639, 2204 и вся группа 114–949) нормативной силы не имеют.
4. Реализовывать пункт из чек-листа шага, а не «всё, что сказано в RFC».

## Известные особенности страниц RFC и индекса

Проверено по всем 92 файлам; важно при доверии к `docs/index.md`:

- **Нумерация приоритетов не непрерывна:** используются 1–25 и 30–96, номера 26–29
  отсутствуют (проверено по всем 92 файлам). Максимальный номер 96 при 92 файлах.
- **Метка и номер приоритета — независимые поля.** Метка привязана к конкретному RFC, а
  не к диапазону номеров: RFC 854 = «20 — Средний приоритет», RFC 1545/775/640/765 =
  16–19 «Справочно / история», RFC 2585/4823 = 22–23 «Низкий приоритет». В этой базе оба
  поля хранятся раздельно.
- **Секция `## Что реализовать` есть только в 17 файлах:** 959, 1123, 2389, 2428, 3659,
  1579, 2577, 2228, 4217, 2640, 7151, 5797, 1635, 6384, 1639, 854, 2585 — то есть у
  приоритетов ≤ 22, с пропусками. В остальных 75 чек-листа нет; требования для них в
  [requirements.md](requirements.md) взяты из `Ключевые положения`, а не придуманы.
- **Явные блоки связей редки:** `## Отменяет` — 4 файла (959, 1639, 5024, 624), `## Отменён`
  — 10 файлов (1545, 171, 172, 264, 265, 354, 542, 607, 765, 2204). Остальные отношения
  описаны словами в тексте, см. [relations.md](relations.md).
- **`docs/rfc-9141.md`** — единственный файл вообще без секции `## Связанные RFC`, и у него
  нет `## Что реализовать` (26 строк, самый короткий в каталоге).
- **Дубли английских названий** (нельзя использовать как ключ): «File Transfer Protocol» — RFC 114, 354, 542; «The File Transfer Protocol» — 172, 265; «The Data Transfer Protocol» — 171, 264; «Comments on the File Transfer Protocol» — 385, 607, 624; «FTP Operation Over Big Address Records (FOOBAR)» — 1545, 1639.
- **Опечатки в источниках оставлены как есть:** `A. McKenize` (вместо McKenzie) в авторах RFC 171 и 264; у RFC 264 год 1972 при соседях 1971.
- **Шаблонная фраза** «Исторический документ ранней эволюции FTP. Для реализации современного сервера нормативной силы не имеет» повторяется дословно в 63 исторических файлах — это отношение *заменён RFC 959*, а не индивидуальное мнение автора страницы.

## Что здесь сознательно не сделано

- Нет перевода и пересказа содержимого RFC — он уже есть в `docs/rfc-*.md`, дублировать смысла нет.
- Нет соответствия «требование → строка в коде заглушки»: кода протокола в репозитории пока нет, ни одна из четырёх заглушек не реализует RFC.
- Нет внешних индексов (QMind, RepoWiki) — по решению пользователя база знаний остаётся локальной и читается офлайн.
