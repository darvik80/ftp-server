# Правила подпроекта `ftp-server-go`

Роль агента и режим ответов задаёт корневой [AGENTS.md](../AGENTS.md). Здесь — только специфика Go.

## Стек и запуск

- Go 1.27 (`go.mod`), внешних зависимостей нет.
- Запуск: `go run .` (из этой папки). Порт/корень — `FTP_PORT`, `FTP_ROOT`.
- На этой машине `go test` упирается в дисковый I/O (25–50 с на полностью кэшированный прогон) — не молотить тесты на каждый чих.

## Текущее состояние

- `main.go` — шаблон GoLand: hello world + TIP-комментарии, протокола нет.
- `internal/config`, `internal/service/server` — по одной строке `package …`, добавлены из IDE.
- `Makefile` — пустой (0 байт), целей нет.

## Конвенции

- Реализация протокола живёт в `internal/`, точка входа `main.go` только собирает конфигурацию и запускает сервер.
- Ошибки передавать через `fmt.Errorf("…: %w", err)`; коды ответов RFC 959 типизировать (первая цифра = класс ответа), а не держать строками в местах вызова.
- Конфигурация только из `internal/config` — значения порта, диапазона пассивных портов и корня каталога не захардкодить.

## Область реализации

Шаг 1 — [RFC 959](../docs/rfc-959.md), [RFC 1123](../docs/rfc-1123.md), [RFC 854](../docs/rfc-854.md); чек-лист брать из [../docs/kb/requirements.md](../docs/kb/requirements.md), не из памяти о протоколе.

## Справочные материалы

Целевая схема сервера — [architecture.md](docs/architecture.md): один движок, три транспорта управляющего соединения, SQLite и общий канал данных. Разборы Go-фреймворков лежат рядом: [go-netty](docs/ref/go-netty.md) и [gnet](docs/ref/gnet.md). В них описаны объекты и интерфейсы, методы, жизненный цикл, модель конкурентности и примеры HTTP/SOCKS5. Эти страницы помогают выбирать механизм реализации, но не заменяют общие требования из [docs/kb/requirements.md](../docs/kb/requirements.md) и не подменяют схему из `architecture.md`.

## На что смотреть в Go именно

- Два соединения (управляющее + данных) — это две разные TCP-сессии на один сокет-Listener нельзя «подменить» одним goroutine-циклом без явной модели состояния сессии.
- Управляющий поток читается как NVT ASCII поверх TCP ([RFC 854](../docs/rfc-854.md)): разделитель CRLF, возможны Telnet IAC-байты.
- Активный режим (`PORT`) требует исходящего подключения сервера к клиенту — на Windows/с firewall это отдельная история с правами и диапазонами.
