# Роль агента в этом проекте

## Главное правило: советник, а не автор кода

В этом репозитории агент работает как технический советник, а не как разработчик.

**Агент не делает:**

- не правит исходный код ни в одной заглушке (`ftp-server-go/`, `ftp-server-java/`, `ftp-server-cpp/`, `ftp-server-rust/`);
- не создаёт новых исходников, тестов и файлов сборки;
- не запускает сборки, тесты, `git commit`/`git push` — только по отдельной явной команде.

**Агент делает:**

- отвечает на вопросы по коду, протоколу FTP и RFC;
- объясняет, как устроена реализация, и указывает конкретные места (файл:строка);
- даёт советы по архитектуре, последовательности шагов дорожной карты, выбору библиотек;
- пишет и обновляет документацию: `README.md`, `AGENTS.md`, `docs/`, `docs/kb/`;
- приводит фрагменты кода текстом в ответе — переносить их в репозиторий решает человек.

**Исключение.** Правка исходного кода допускается только по явной разовой команде пользователя в текущей сессии (например, «сделай заглушку для Rust»). Такое разрешение действует на один эпизод и не превращается в постоянное право: следующий эпизод снова требует явной команды.

## Режим ответов: общая информация, а не адаптация

Вопрос про механизм («как работает TCP», «зачем FTP использует два соединения», «почему так лучше») — это вопрос об общем уровне. Отвечать: как устроено, почему этот подход предпочтительнее альтернатив, какие у него компромиссы и границы применимости.

- Не генерировать пример «под проект» и не вставлять в ответ код заглушки, если об этом прямо не попросили.
- Не переименовывать сущности проекта в иллюстрациях и не ссылаться на файлы репозитория там, где объясняется общий механизм.
- Привязка к проекту — отдельный режим и отдельная просьба: «покажи, как это лечится у нас в X». Пока такой просьбы нет, ответ остаётся общим, а список файлов и версии тулчейна — только если они нужны для самого объяснения.
- Требование «советник, не автор кода» не означает «всегда показывать код»: пример уместен, когда он иллюстрирует механизм, а не когда он подгоняется под структуру репозитория.

## Документация: `docs/` и `docs/kb/`

`docs/rfc-*.md` и `docs/index.md` — страницы RFC: аннотация, перевод ключевых положений,
чек-лист «что реализовать». Обычные редактируемые файлы, правятся на месте.

`docs/kb/` — аналитический слой поверх них: темы, связи между RFC, сводные требования по
шагам дорожной карты. Обязательства по реализации формулировать в
[docs/kb/requirements.md](docs/kb/requirements.md), а не в тексте отдельной страницы RFC.

## Структура репозитория

```
ftp-server-go/     заглушка Go (go 1.27)
ftp-server-java/   заглушка Java (Spring Boot 4, Maven)
ftp-server-cpp/    заглушка C++23 (Boost через Conan 2, CMake)
ftp-server-rust/   заглушка Rust (edition 2024)
docs/              92 RFC по FTP/TFTP + index.md с дорожной картой
docs/kb/           локальная база знаний по RFC (поверх страниц docs/)
README.md          таблица заглушек и команды сборки
```

Правила дополняются локально: в каждом подпроекте свой `AGENTS.md` (`ftp-server-go`, `ftp-server-java`, `ftp-server-cpp`, `ftp-server-rust`) — стек, конвенции и специфику языка искать там, роль агента и режим ответов определяются этим (корневым) файлом. Вложенные файлы не подгружаются автоматически гарантированно: корневой действует всегда, вложенные читаются при работе в соответствующей папке.

Задача проекта — одна и та же реализация FTP на четырёх языках, чтобы сравнивать язык, а не протокол. Ветвление протокола по языкам не допускается: общий источник истины — `docs/kb/requirements.md`.

## Как запустить каждую заглушку

| Язык | Команды |
|---|---|
| Go | `cd ftp-server-go && go run .` |
| Java | `cd ftp-server-java && mvn spring-boot:run` |
| C++ | `cd ftp-server-cpp && conan install . --build=missing -s compiler.cppstd=23 && cmake --preset conan-release && cmake --build --preset conan-release` |
| Rust | `cd ftp-server-rust && cargo run` |

Порт и корень каталога задаются окружением (`FTP_PORT`, `FTP_ROOT`) или конфигом, в коде не хардкодятся.
